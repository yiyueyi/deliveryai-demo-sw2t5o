## 1. 背景与目标

### 1.1 背景
仓库已存在一个完整的 React + Vite 火锅点餐应用 `hdl-order-demo`，功能覆盖分类、菜单、规格、购物车、下单与结算，但需 `npm install && npm run dev/build` 才能运行，不便用于"双击即开"的快速预览与评审。需求方明确要求一个**可直接在浏览器打开、优先原生技术、便于预览和维护**的点餐页面。

### 1.2 目标
- 用单个 `.html` 文件完整呈现点餐核心闭环，零构建、零外部网络依赖。
- 视觉与交互对齐现网设计系统，确保从原型到正式开发的体验连续。
- 为后续真实开发节点提供可直接参照的交互基线与参考代码。

### 1.3 非目标
- 不替代现有 React 应用，不接入真实后端 / 支付 / 库存 / 登录。
- 不做履约、退菜、呼叫服务、多语言、老人模式等增强能力（见需求澄清 Spec §2.2）。

---

## 2. 用户与使用场景

- **主用户**：到店自助点餐顾客。
  - 场景 A：按分类浏览，挑菜、选规格、加入购物车。
  - 场景 B：用搜索快速找到目标菜品。
  - 场景 C：调整已选数量、核对金额、结算支付、获得成功反馈。
- **次用户**：产品 / 设计 / 研发评审者，双击文件即可走查完整交互。

---

## 3. 信息架构与页面结构

单页面，无路由跳转，通过弹层完成规格选择 / 结算 / 成功反馈：

```
顶部栏（品牌 · 营业状态 · 桌台）
└── 主体两栏（≥980px）/ 单列（<980px）
    ├── 菜单区
    │   ├── Hero 横幅
    │   ├── 搜索框
    │   ├── 分类胶囊（推荐/锅底/牛羊肉/海鲜河鲜/蔬菜豆品/主食饮品）
    │   └── 菜品卡片网格（图、标签、名、描述、价格、加购按钮）
    └── 购物车侧栏（仅桌面）：商品行、数量步进器、小计、合计、去结算
移动端底部常驻结算条（购物车入口 + 合计 + 去结算）
弹层：规格选择 / 购物车抽屉（移动）/ 结算 / 下单成功
全局：Toast 轻提示
```

## 4. 功能性需求（Functional Requirements）

> 优先级：P0 为验收必达，P1 为体验增强。

### F1 菜品分类与列表（P0）
- F1.1 展示 6 个分类；"推荐"为默认分类，展示全部菜品。
- F1.2 点击分类即时筛选列表；当前分类高亮（chili 红底白字）。
- F1.3 菜品卡片展示：插画图、营销标签（如人气 No.1/招牌/主厨推荐/新品）、名称、描述、起售价、加购"＋"按钮。
- F1.4 菜品数据共 10 个示例 SKU，覆盖 5 个具体分类（数据见附录 A）。

### F2 搜索（P1）
- F2.1 顶部搜索框，按菜品名称或描述做包含匹配，实时过滤。
- F2.2 搜索可与分类叠加生效。
- F2.3 无结果时展示空状态文案"没有找到「关键字」相关的菜品…"。

### F3 菜品规格选择与加入购物车（P0）
- F3.1 点击"＋"打开规格弹层，展示菜品图、描述、当前单价。
- F3.2 按菜品配置动态展示可选项：份量（半份/整份）、口味、辣度；默认选中合理首项（份量默认整份）。
- F3.3 切换"半份"时单价按 0.58 系数实时重算（见业务规则 R1）。
- F3.4 选择"超级辣"弹出二次风险确认（`confirm`），取消则不采用、保留原辣度。
- F3.5 点击"加入购物车"，按"菜品 + 规格"合并：相同则数量 +1，否则新增一行；随后给出 Toast 并关闭弹层。

### F4 购物车（P0）
- F4.1 展示每个已选项：图、名称、规格串、单价×数量后的行金额、数量步进器。
- F4.2 步进器"＋/−"调整数量；数量为 1 时点"−"移除该项并提示。
- F4.3 实时展示总份数、菜品小计、预估合计（未优惠口径）。
- F4.4 空购物车展示空状态插画与引导文案，不展示合计/提交按钮。
- F4.5 桌面端在右侧侧栏操作；移动端通过底部购物车按钮打开抽屉操作。

### F5 结算（P0）
- F5.1 从侧栏"去结算"或移动端底部条进入；空车时入口禁用/提示。
- F5.2 结算弹层展示：逐行明细（名称 × 数量 · 规格 = 行金额）、菜品小计、优惠、应付合计。
- F5.3 优惠规则：菜品小计 ≥ ¥100 减 ¥30；未达门槛展示规则说明、优惠为 0。
- F5.4 支付方式二选一：移动支付（默认）/ 桌边 POS。
- F5.5 主按钮文案展示应付金额"确认支付 ¥X"。

### F6 下单 / 支付成功反馈（P0）
- F6.1 确认支付后进入成功态：成功图标、"下单并支付成功"、生成的订单号、份数、支付方式、后厨提示、本次实付金额。
- F6.2 下单成功后清空购物车，侧栏与底部条份数/金额归零。
- F6.3 提供"完成，继续点餐"关闭弹层；"查看账单明细"给出原型说明提示。

### F7 全局交互（P1）
- F7.1 点击遮罩空白处或"✕"、按 `Esc` 关闭弹层。
- F7.2 关键操作均有 Toast 反馈（加入、移除、空车结算等）。
- F7.3 弹层打开时锁定背景滚动。

## 5. 非功能性需求（Non-Functional Requirements）

### N1 可移植性 / 零依赖（P0）
- 单个自包含 `ordering.html`，**不引用任何外部 CSS/JS/字体/图片 URL**；插画用 emoji，图标用内联 SVG。
- 支持 `file://` 协议双击直接打开，也支持任意静态服务器托管；无需构建。

### N2 兼容性（P0）
- 兼容主流 evergreen 浏览器（Chrome / Edge / Safari / Firefox 近两年版本）。
- 仅使用广泛支持的 ES5 安全子集 + 常规 CSS（Flexbox/Grid/媒体查询），不依赖框架。

### N3 响应式（P0）
- 断点：`<560px` 菜品单列，`560–979px` 双列，`≥980px` 菜单 + 购物车双栏（菜单 1fr / 购物车 380px）。
- 移动端（`<980px`）隐藏侧栏购物车，使用底部固定结算条 + 底部抽屉式弹层；适配刘海屏安全区 `env(safe-area-inset-bottom)`。
- 分类条横向可滚动；购物车明细区限高滚动。

### N4 可用性与可访问性（P1）
- 触控目标 ≥ 38px；按钮含 `aria-label`；弹层 `role="dialog"` + `aria-modal`；搜索框有关联 label。
- 文字与背景对比度满足基本可读性；价格/主操作使用强调色 chili。

### N5 性能（P1）
- 单文件体积小（约 36KB 级），本地打开首屏即时呈现；列表为内存过滤，交互无网络往返。

### N6 可维护性（P1）
- 数据（`CATEGORIES` / `DISHES`）与渲染、状态逻辑分区组织；新增菜品仅需在 `DISHES` 数组追加一条。
- 设计色值集中在 `:root` CSS 变量，便于换肤。

### N7 安全与稳健（P2）
- 所有动态文本经 HTML 转义后再插入，避免注入；`localStorage` 不使用，无隐私数据。

## 6. 业务规则汇总

| 编号 | 规则 | 备注 |
| --- | --- | --- |
| R1 | 半份价 = round(原价 × 0.58) | 沿用现网，待业务最终确认 |
| R2 | 购物车合并键 = 菜品 ID + 规格串 | 不同规格独立成行 |
| R3 | 合计 = Σ 单价 × 数量 | 优惠前口径 |
| R4 | 满 ¥100 减 ¥30，应付 = 小计 − 优惠 | 原型沿用现网，待业务确认 |
| R5 | "超级辣"需二次风险确认 | 沿用现网风控 |
| R6 | 下单成功生成原型订单号 `FD + 年月日时分秒`，并清空购物车 | 非真实单号 |
| R7 | 空车不可结算；搜索无结果有空状态 | 边界 |

## 7. 验收标准（Acceptance Criteria）

| # | 验收点 | 预期结果 | 本次实测 |
| --- | --- | --- | --- |
| AC1 | 查看示例菜品及价格 | 分类可见，10 个菜品含名称/描述/价格 | ✅ 浏览器实测 |
| AC2 | 选择菜品并调整数量 | 可选规格加购，购物车步进器可增减、可移除，半份按 0.58 计价 | ✅ 实测（¥42→半份¥24，数量 2 行金额¥48） |
| AC3 | 购物车展示已选/数量/总价 | 明细、份数、小计/合计正确联动 | ✅ 实测（¥24×2 + ¥68 = ¥116） |
| AC4 | 结算/下单明确反馈 | 明细+满减+应付，支付成功页含订单号/份数/支付方式/实付并清空购物车 | ✅ 实测（满减−¥30，应付/实付¥86） |
| AC5 | 桌面与移动宽度可浏览操作 | 双栏/单列切换，移动端底部条+抽屉正常 | ✅ 实测（1280px 与 390px 视口） |
| AC6 | 零依赖直接打开 | `file://` 双击可用、无外链请求 | ✅ 单文件，内联资源 |
| AC7 | 搜索与分类 | 关键字过滤、分类筛选、空状态正确 | ✅ 实测（"虾"→鲜虾滑；蔬菜豆品 2 项） |

## 8. 待确认项与后续建议

- `待确认（业务）`：满减门槛/金额、半份 0.58 系数、超级辣文案是否为正式规则。
- `技术待设计`：真实菜品/分类/价格接口、订单号与优惠的计算归属（前端 or 后端）、库存售罄。
- `建议`：进入正式开发时，可将本原型的状态模型（cart 合并、计价、结算）迁移到现有 React 应用或保持轻量多页方案，由 Spec/技术设计节点评估。
